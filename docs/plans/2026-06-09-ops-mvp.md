# Plan: Operator email notifications + Ops console (MVP)

> Hand-off plan for the dev agent. Written 2026-06-09. Branch: `feat/ops-console`.
> Read `CLAUDE.md` first — all architecture constraints there apply. Plan-relevant ones
> are restated inline where they bite.

## Context — why this exists

Fulfillment is manual by design, but today the operator half of the loop doesn't exist:

- `notifyOperator()` (`src/lib/notify.ts`) is a `console.info` → lands in Vercel runtime
  logs, which are short-retention and never alert anyone. As a notification channel it is
  effectively `/dev/null`.
- The **durable data is fine** — every request/tab line/guest is a row in Supabase
  Postgres. Nothing is lost. But the only way to see or act on it is Prisma Studio / SQL.
- There is **no UI anywhere** to quote a QUOTE-priced request, confirm/decline, or mark a
  PENDING tab line CHARGED. The guest-side lifecycle dead-ends at "Requested."

This plan delivers: (A) real email notifications, (B) per-line internal economics in the
schema, (C) a minimal internal operator console at `/ops` where Parker fulfills requests.

**Scope note:** `CLAUDE.md` lists "PM dashboard / admin panel" as out of scope. That line
means **PM-facing** dashboards. This `/ops` console is the internal operator surface and
is explicitly approved (Parker, 2026-06-09). Final step of this plan updates CLAUDE.md to
say so.

## Phase A — Operator email notifications (Resend)

**Goal:** a guest action produces an email in Parker's inbox within seconds. The guest
action must NEVER fail or slow down because email failed.

1. **No new npm dependency.** Send via plain `fetch` to `https://api.resend.com/emails`
   (one POST; the SDK isn't worth a dep). Bearer auth with `RESEND_API_KEY`.
2. **Env vars** (add to `.env.example` with comments, real values in `.env` / Vercel
   dashboard — paste in the dashboard UI, never `vercel env add` from PowerShell):
   - `RESEND_API_KEY` — from resend.com (free tier: 100/day, plenty)
   - `OPERATOR_EMAIL` — where notifications go
   - `APP_BASE_URL` — e.g. `https://summit-guest-app.vercel.app`, used for deep links
     in emails (and by Phase C's ops-link script). Server-only, not `NEXT_PUBLIC_`.
3. **Rework `src/lib/notify.ts`** (keep the `OperatorEvent` union and call-site API
   unchanged — `requests.ts` and `payments.ts` should not need edits):
   - If `RESEND_API_KEY` or `OPERATOR_EMAIL` is unset → keep current `console.info`
     behavior (dev/local works with zero config, build never breaks).
   - Otherwise send a plain-text (or minimal HTML) email AND still `console.info`.
   - Wrap the send in try/catch; on failure `console.error` and return. Never throw.
   - Sender: `onboarding@resend.dev` works out of the box but only delivers to the
     Resend account owner's address — fine for single-operator MVP. Note in
     `.env.example` that a verified domain sender is the upgrade path.
4. **Email content** — subject like `[Summit] Airport Transfer — Parker T. @ Fawngrove`,
   body with: guest name, property, service, requested date/time, party size, notes,
   whether it needs a quote (`QUOTE` price unit → "ACTION: needs quote"), and a deep
   link to `${APP_BASE_URL}/ops/stays/${stayId}` (Phase C page).
5. Keep `card_added` event wired too (it signals an engaged guest — worth a ping).

## Phase B — Schema: per-line internal economics

**Goal:** start recording the demand-router economics on every transaction, per the
standing architecture decision in CLAUDE.md ("Reserve internal per-line economics").

1. **Migration** adding to `TabLineItem`:
   ```prisma
   vendorCostCents Int? // internal: what the vendor charges us
   pmShareCents    Int? // internal: PM rev-share (Phase-2; 0/null today)
   netCents        Int? // internal: amount - vendorCost - pmShare, computed on write
   ```
   All nullable — backfill is not required. `npx prisma migrate dev --name tab_line_economics`.
2. **Guardrail (hard rule):** these three fields are INTERNAL ONLY. Never render them in
   any guest-facing page or pass raw `TabLineItem` rows into a client component. Current
   guest code is already safe (server components render explicit fields; `Wallet.tsx`
   receives a narrowed object) — keep it that way. Add a one-line comment on the fields
   in `schema.prisma`: `// NEVER guest- or PM-facing`.
3. `netCents` is computed and stored whenever economics are set (Phase C action), not a
   DB computed column. Net target 15–20% — show the % in the ops UI so drift is visible.

## Phase C — Ops console at `/ops`

**Goal:** overhead view + per-stay detail + the fulfillment actions. Internal tool:
utilitarian styling, plain and dense. Do NOT spend time making it luxury — the guest app
aesthetic does not apply here. No new UI libraries.

### C1. Access (no auth library — mirrors the guest-token pattern)

- New env var `OPS_KEY` — long random secret (`openssl rand -base64 32` equivalent).
- `src/lib/opsSession.ts`:
  - `requireOperator()` — reads httpOnly cookie `summit_ops`, constant-time compares
    its value to `process.env.OPS_KEY` (use `timingSafeEqual`; length-check first).
    On mismatch/absence → `redirect("/invalid")` (reuse the existing page; don't
    advertise that /ops exists).
  - Cookie options: httpOnly, secure in prod, sameSite lax, path `/`, maxAge 90d.
- Entry route `src/app/ops-key/[key]/route.ts` (outside `/ops` so the gate has one
  door): constant-time compare `key` → set cookie → redirect `/ops`. Invalid → `/invalid`.
- `scripts/ops-link.ts` + npm script `"ops:link"` — prints `${APP_BASE_URL}/ops-key/${OPS_KEY}`
  so Parker can mint/bookmark the link on his phone. (Same spirit as `npm run token`.)
- Rotation = change `OPS_KEY` in Vercel. Good enough for a single operator; revisit if a
  second human ever joins.

### C2. Routes (server components; new route group, NOT inside `(trip)` — no BottomNav, no guest layout)

- `src/app/ops/layout.tsx` — calls `requireOperator()`, minimal header, dense styling.
- `src/app/ops/page.tsx` — **overview**:
  - "Needs action" queue: `ServiceRequest` with status `REQUESTED` (quote needed),
    then `CONFIRMED` with `requestedFor` in the next 48h (delivery coming up).
  - Stays table (upcoming + in-house): guest name, property, dates, party size, tab
    total (pending/charged split), token `lastAccessedAt` (engagement signal), link to
    detail.
  - Recent activity: last ~20 of (requests created, tab lines charged), newest first.
- `src/app/ops/stays/[stayId]/page.tsx` — **per-guest detail**:
  - Header: guest + contact (email/phone/notes), property, dates, party, token
    last-accessed.
  - Requests section: every `ServiceRequest` with status, requested-for, notes, and the
    action forms (below). QUOTE requests get an inline quote form (amount + vendor cost).
  - Tab section: all lines with amount, status, and the internal economics columns
    (vendor cost / PM share / net + net-%); charge button on PENDING lines; inline
    economics edit; "add manual line" form (description + amount + vendor cost) for
    off-catalog items.
  - Itinerary section: read-only list (editing itinerary items is out of scope).
- Ops queries live in `src/lib/opsQueries.ts` (keep `queries.ts` guest-only so it stays
  obvious which surface sees what).

### C3. Server actions — `src/app/actions/ops.ts`

Every action starts with `requireOperator()`. After mutating, `revalidatePath` the ops
pages AND the touched guest pages (`/`, `/tab`, `/itinerary`).

- `quoteRequest(requestId, amountCents, vendorCostCents?)` — sets `quotedAmount`,
  status → `CONFIRMED`, creates the PENDING `TabLineItem` (with economics + computed
  `netCents`), and if `requestedFor` is set creates the linked `ItineraryItem` (reuse
  `serviceToItineraryCategory`; same shape as the auto-confirm path in
  `src/app/actions/requests.ts` — extract a small shared helper rather than duplicating).
- `setRequestStatus(requestId, status)` — allowed: `SCHEDULED`, `COMPLETED`, `DECLINED`,
  `CANCELLED`. On DECLINED/CANCELLED: void linked PENDING tab lines (status `VOID`) and
  delete the linked itinerary item if any. Validate the transition makes sense (e.g.
  can't complete a DECLINED request); keep it a simple allowlist map.
- `chargeTabLine(tabLineItemId)` — looks up the stay's default `PaymentMethod`; calls
  `paymentProvider.chargeService(...)` (the existing seam — mock today, Stripe later);
  on success sets status `CHARGED` + `externalRef`. No card on file → return a clear
  error to the form.
- `setLineEconomics(tabLineItemId, vendorCostCents, pmShareCents)` — stores both,
  recomputes `netCents = amount - vendorCost - pmShare`.
- `addManualTabLine(stayId, description, amountCents, vendorCostCents?)` — PENDING line,
  no service request linked.

Use the existing `useActionState`/form patterns from `RequestForm.tsx` where a client
component is genuinely needed (quote/charge forms); prefer plain `<form action={...}>`
server forms elsewhere.

## Acceptance checklist (run before PR)

1. `npm run lint` + `npm run typecheck` clean.
2. `npm run db:seed` → open demo link → request a **fixed-price** service →
   email arrives at `OPERATOR_EMAIL`; line shows PENDING on guest tab; request and line
   visible on `/ops` and the stay detail.
3. Request the **QUOTE** service (grocery) → email says "needs quote" → quote it in
   `/ops` with a vendor cost → guest tab shows the line; itinerary item appears if dated;
   net % displays correctly in ops.
4. Charge a PENDING line in `/ops` → guest tab flips to "Settled"; `externalRef`
   populated (mock).
5. Decline a REQUESTED request → linked line voids, itinerary item gone, guest totals
   correct.
6. With `RESEND_API_KEY` unset locally, all guest flows still work (console fallback).
7. `/ops` with no/garbage cookie → `/invalid`. Wrong key in `/ops-key/[key]` → `/invalid`.
8. Grep `vendorCostCents|pmShareCents|netCents` — appears ONLY in schema, ops files, and
   migrations. Zero hits under `src/app/(trip)` or `src/components` (except nothing).
